## 1 Заказы за сутки n ≤ 200 000

Есть ли среди номеров хотя бы два одинаковых

- **Проходит:** Да но только через хеш таблицу set
- **Решение:** Иду по списку один раз каждый номер кидаю в set Если номер там уже лежит сразу возвращаю True Дошёл до конца значит повторов нет возвращаю False
- **Что мешало проще:** В лоб двумя циклами сравнить каждую пару Это O(n²)
- **Почему это верно (с числом):**  
  Парами 200000² = 4·10¹⁰ сравнений При лимите 10⁷ операций в секунду это ~4000 секунд не вариант  
  Через set 200000 операций то есть доли секунды Разница в 200000 раз

## 2 Цены на складе n ≤ 100 000

Найти три самые дешёвые позиции

- **Проходит:** Да можно и сортировкой и одним проходом
- **Решение:** Держу три переменные под минимумы и на каждом элементе проверяю не влезает ли он в тройку Так прохожу массив ровно один раз
- **Что мешало проще:** Отсортировать весь массив и взять первые три Работает но сортирует лишние 99997 элементов
- **Почему это верно (с числом):**  
  Один проход 100000 операций  
  Сортировка 100000·log₂(100000) ≈ 1 7·10⁶ операций Обе укладываются но первая в 17 раз быстрее

## 3 Архив чеков n ≤ 10⁷ запросов q ≤ 10⁵

Отсортирован По каждому запросу сказать есть ли такой чек

- **Проходит:** Да но только бинарным поиском
- **Решение:** На каждый запрос запускаю бинарный поиск по отсортированному массиву делю область пополам пока не найду или не схлопнется
- **Что мешало проще:** На каждый запрос идти линейно по всему архиву Это O(n·q)
- **Почему это верно (с числом):**  
  Линейно 10⁷ · 10⁵ = 10¹² операций Это ~28 часов при 10⁷ оп с не пройдёт  
  Бинарно 10⁵ · log₂(10⁷) ≈ 10⁵ · 24 = 2 4·10⁶ операций Четверть секунды

## 4 Координаты курьеров n ≤ 3 000

Найти двух ближайших друг к другу

- **Проходит:** Да обычным перебором пар
- **Решение:** Двойной цикл считаю манхэттенское расстояние для каждой пары запоминаю минимум
- **Что мешало проще:** Можно было сортировать по x и смотреть только соседей но это заметно сложнее в коде а выигрыш здесь не нужен
- **Почему это верно (с числом):**  
  Пар ровно n(n 1)/2 = 3000·2999/2 ≈ 4 5·10⁶ При лимите 10⁷ влезает с запасом Если бы n было 10⁵ пар стало бы 5·10⁹ уже не прошло бы

## 5 Одно число k ≤ 10⁹

Сколько раз его можно разделить пополам до единицы

- **Проходит:** Да обычный while
- **Решение:** Пока k больше 1 делю нацело на 2 и считаю шаги
- **Что мешало проще:** Ничего задача сама по себе простая
- **Почему это верно (с числом):**  
  Число шагов равно log₂(k) Для k = 10⁹ это ≈ 30 Тридцать операций это мгновенно

## 6 Две накладные n ≤ 10⁵ и m ≤ 10⁵

Обе отсортированы Собрать из них один отсортированный список

- **Проходит:** Да классическим слиянием
- **Решение:** Два указателя на каждом шаге сравниваю текущие элементы и меньший кладу в результат Когда один список кончился приклеиваю остаток второго
- **Что мешало проще:** Свалить всё в кучу и вызвать sort Работает но лишняя работа
- **Почему это верно (с числом):**  
  Слияние n + m = 200000 операций  
  Сортировка 200000·log₂(200000) ≈ 3 6·10⁶ операций Обе влезают но слияние в 18 раз быстрее и использует уже имеющуюся упорядоченность

## 7 Где модель ошиблась

**Условие №:** 1  
**Что ответила модель:** Решается за O(n) через set всё ок  
**Что не так:** Она не сказала про память В худшем случае когда все номера разные set хранит все n элементов это O(n) дополнительной памяти  
**Как поймали (расчёт или запуск):** Прикинул 200000 номеров × ~8 байт на элемент в set ≈ 1 6 МБ Для этой задачи ерунда но если бы n было 10⁷ то уже 80 МБ и это надо было упомянуть
